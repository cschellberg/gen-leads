# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal lead-gen toolkit. It builds a list of prospect companies (currently sourced from LinkedIn company search), enriches each one (website, contact, a 1-10 fit ranking, a drafted cold-outreach email via Gemini), and lets the owner review/send emails through a set of small Tkinter desktop apps. Everything reads/writes one shared SQLite database (`leads.db`) via SQLAlchemy models in `db.py`. Multiple businesses/identities can share that one database via `Profile` rows -- see Architecture below.

There is no test suite, build step, linter config, or packaging — this is a single-user local toolkit, run directly with `python <script>.py`.

Entry points (each is an independent standalone Tkinter app — see "Architecture" below):
- `python main_app.py` — the one real window in normal use. An Apps menu embeds the other GUI apps into its content area one at a time (lazy-imported on first open, no separate windows), plus a Profile dropdown (selects which `db.Profile` newly-scraped leads get tagged with)
- `python lead_runs_app.py` — log/view scrape coverage, and run the enrichment pipeline ("Process" button) on unprocessed leads
- `python leads_app.py` — browse/edit/disable leads and send drafted emails via Gmail SMTP (as each lead's own `Profile.email`)
- `python verify_email_app.py` — standalone SMTP mailbox-existence probe (GUI wrapper around `verify_email.py`)
- `python profile_app.py` — manage `Profile` rows (sender email + overview/decision-maker/signature-block text)

CLI/batch scripts (no GUI):
- `python lead_gen.py [--db PATH] [--limit N] [--sleep SECONDS]` — runs the enrichment pipeline over every unprocessed lead. `--limit` is for smoke-testing since it makes real Gemini API calls per lead.
- `python regenerate_emails.py [--limit N] [--force] [--sleep SECONDS]` — redrafts subject/body for existing leads via `lead_gen.draft_email()` without repeating the website/contact search or ranking. Use this (not `lead_gen.py`) after changing the email prompt/style/blurb, so existing leads' emails get updated without re-spending on search+ranking. Note: as currently written, its lead-filtering logic is commented out, so it reformats **every** lead in the DB each run, not just badly-formatted ones — check `todo = ...` near the top before assuming `--force` is required to do a full pass.
- `python fix_website_and_email.py [--website-only] [--rediscover-websites] [--limit N] [--sleep SECONDS] [--dry-run]` — one-time corrective script for pre-existing bad `website`/`email` data (subpage instead of homepage, wrong domain entirely, or a URL/blank instead of a real email address). `--rediscover-websites` re-picks every website's domain via Gemini and re-checks contacts for any lead whose domain changes as a result. Safe to re-run — only touches rows that still look wrong.
- `python categorize_leads.py [--limit N] [--sleep SECONDS] [--dry-run]` — one-time backfill that assigns a `category` (from `db.CATEGORIES`) to every processed lead with `category=""` (i.e. it predates that column). New leads get categorized automatically during `lead_gen.py`'s normal enrichment, so this only needs to be re-run if old rows are reset.
- `python migrate_to_profile.py [--db PATH] [--email ADDR] [--overview-file PATH] [--decision-maker-file PATH] [--signature-block-file PATH]` — one-time: creates a `Profile` row from the (now-legacy) file-based defaults `overview.md`/`decision_maker.md`/`signature_block.md` and links every lead *and lead_run* with `profile_id IS NULL` to it. Safe to re-run (skips creating a duplicate profile for an email that already has one; only re-links still-unlinked rows).
- `scripts\install.ps1` — PowerShell setup script for a fresh machine (e.g. handing this project to a non-technical user): installs Python 3.13 via winget if missing, creates `.venv` at the project root if missing, then `pip install -r requirements.txt` into it. Idempotent — safe to re-run, and once `.venv` exists, re-running never touches the system Python again, only `.venv`.

Safety flags:
- `LEADS_GUI_DRY_RUN=1` (env var) — makes `leads_app.py`'s Send button print the email instead of actually sending over SMTP. The DB is still updated exactly as on a real send. Always use this for testing; never send real mail from a test run.

Required `.env` keys (project root, loaded via `python-dotenv`'s `load_dotenv()`): `GOOGLE_API_KEY` (Gemini — used both via the OpenAI-compatible endpoint and the native `google-genai` client, see below), `GMAIL_APP_PASSWORD` (a Gmail App Password — see setup instructions in `leads_app.py`'s docstring; every `Profile.email` needs to be an address this one app password can authenticate as, e.g. aliases on the same Gmail account, since there's no per-Profile credential yet). `S3_BUCKET` is also required for `leads_app.py`'s "Backup DB" button (uploads `leads.db` to that S3 bucket as `leads<yyyyMMdd>.db`; relies on AWS credentials being available via boto3's normal credential chain, e.g. `~/.aws/credentials` — not stored in `.env`).

`DEFAULT_DB` is always `leads.db` next to `db.py` — no env override. This used to be configurable via a `DATABASE_NAME` env var (a separate SQLite file per user/business), and the sender email / overview / decision-maker / signature-block texts used to be configurable via `SENDER_EMAIL` / `OVERVIEW_FILE` / `DECISION_MAKER_FILE` / `SIGNATURE_BLOCK_FILE`. All of that is superseded by the `Profile` table (see Architecture) — one shared database, `Profile` rows managed in `profile_app.py` instead of env vars/files. If you see any of those five env vars still set in `.env`, they're inert leftovers safe to delete.

## Architecture

**Two tables via `db.py`: `Lead` and `Profile`, many-to-one.** `Lead` (table `leads`), `Profile` (table `profiles`), and `LeadRun` (table `lead_runs`) are the only SQLAlchemy models, and every app/script imports them from `db.py` rather than redefining anything. `get_engine()` calls `Base.metadata.create_all()` (creates missing tables only) plus a hand-rolled `_add_column_if_missing()` migration step — since SQLAlchemy's `create_all()` never alters existing tables, any new column added to `Lead` needs a corresponding `ALTER TABLE` added there (`default_sql` lets it be `"0"` for BOOLEAN/INTEGER, `"''"` for TEXT like `category`, or `"NULL"` for a nullable FK like `profile_id`). Note this ALTER TABLE doesn't add a real FK constraint (SQLite ALTER TABLE ADD COLUMN can't retrofit one onto an existing table the way `create_all()` does for a brand-new one) -- functionally fine, since nothing here enables `PRAGMA foreign_keys` enforcement anyway; SQLAlchemy's ORM-level `relationship()` navigation works regardless. `DEFAULT_DB` is always `leads.db`, resolved relative to `db.py`'s own location, not the CWD, so scripts behave the same regardless of where they're invoked from -- no env override (see the `.env` note above for what this replaced). `db.CATEGORIES` is the fixed list of industry categories a lead can be tagged with — the single source of truth shared by `lead_gen.py` (assigns one via a `Literal[*CATEGORIES]` field during enrichment), `leads_app.py` (filter dropdown + edit-panel combobox), and `categorize_leads.py` (backfill for pre-existing rows). Change the list in one place if it needs to grow.

**`Profile` (table `profiles`) is a business/user identity.** Columns: `email` (sender address), `overview`, `decision_maker`, `signature_block` (all `Text`) -- these three used to be `overview.md` / `decision_maker.md` / `signature_block.md` files, now DB-backed and editable via `profile_app.py` instead. `Lead.profile_id` (nullable FK to `profiles.id`) + `Lead.profile` / `Profile.leads` relationships make it many-leads-to-one-profile: one shared `leads.db` can serve multiple businesses/users at once, each lead enriched/drafted/sent under the correct identity's content and email. `lead_gen.resolve_lead_profile(session, lead)` is the one place that decides which profile a lead uses: returns `lead.profile` if already set; if not, auto-assigns (and persists) the sole `Profile` row if exactly one exists (the common single-business case, and how a lead gets its first profile after `migrate_to_profile.py`'s backfill); otherwise raises `lead_gen.MissingProfileError` -- zero or multiple profiles makes the right one genuinely ambiguous, so this never guesses. `process_unprocessed_leads()` re-raises `MissingProfileError` (alongside `FileNotFoundError`, for a missing `email_example.md`) to stop the *whole run* rather than silently marking leads `processed=True` with no real content -- see the point below about that failure mode. `profile_app.py`'s delete flow nulls out `profile_id` on any leads that pointed to a deleted profile rather than leaving a dangling id. `LeadRun` has the identical shape (`LeadRun.profile_id` nullable FK + `LeadRun.profile` / `Profile.lead_runs`, many-runs-to-one-profile) attributing a scrape to whichever Profile it was done for -- `linkedin_import.ingest_linkedin_page_text()`'s `profile_id` param (see below) sets it on both the new `Lead` rows and the `LeadRun` row it logs in the same call.

**Idempotent, stage-gated pipeline via `processed`/`disabled` flags on each lead** (no separate job queue or status table):
1. **Import** (`linkedin_import.py`): parses LinkedIn company-search result page text (fetched by a human/agent-driven real browser session — this module never fetches anything itself, deliberately, to avoid LinkedIn ToS/ban risk) and inserts new companies as `processed=False`, tagged with `profile_id` if the caller passes one (`main_app.py`'s Profile dropdown embeds the selected id into `lead_runs_app.py`'s generated Copy Scrape Prompt text). Dedup is by a symbol-stripped, case-insensitive company name match. Logs one `LeadRun` row per page range ingested, tagged with that same `profile_id`.
2. **Enrich** (`lead_gen.py`'s `process_unprocessed_leads()` / `process_company()`): for each `processed=False` lead, first `resolve_lead_profile()` (see above), then -- Gemini web-search-grounded lookup (`find_website()`) for the official homepage (never a subpage), Gemini web-search-grounded lookup (`find_contact()`) for a named contact matching that Profile's `decision_maker` text (falls back to `generate_email_permutations()` guesses off the domain when a name but no email is found, then a confirmed generic email; the stored `email` is always real address(es), comma-separated if multiple guesses, never a URL), Gemini-drafted ranking (1-10) + industry `category` (one of `db.CATEGORIES`, same structured-output call as the ranking, no extra API cost) + subject/body drafted under that Profile's `overview`/`signature_block`. Every lead is marked `processed=True` when done (even on an ordinary per-lead failure -- bad search result, flaky API response -- so a permanently-broken lead isn't retried/re-billed forever); the one exception is a setup problem (`MissingProfileError` or a missing `email_example.md`), which stops the whole run instead, leaving that lead and everything after it `processed=False` for a re-run once fixed.
3. **Review & send** (`leads_app.py`): browse/filter/edit leads, then send via Gmail SMTP *as that lead's own `Profile.email`* (not a global sender constant) -- `open_send_panel()` shows it read-only as "Sending as" and errors out up front if the lead has no profile rather than falling back to some default. `times_contacted` increments and the (possibly edited) email/subject/body are persisted only on a *successful* send.

**Email drafting is centralized in `lead_gen.draft_email()`.** `regenerate_emails.py` deliberately imports and reuses it rather than reimplementing drafting, "so the two scripts can never drift out of style with each other" — when changing how emails are worded/styled, edit the relevant `Profile` row (via `profile_app.py`) and/or `draft_email()`/`email_example.md` in code, then re-run `regenerate_emails.py` to backfill existing rows rather than patching `leads.db` bodies directly (bodies are free-form LLM text, not templated, so find/replace across rows is unreliable — regenerating is the correct way to bulk-update wording). `draft_email()` and `find_contact()` both now take the relevant Profile text(s) as plain string parameters (`overview_blurb`, `signature_block`, `decision_maker_description`) rather than loading them themselves -- callers (`process_company()`) resolve the Profile once via `resolve_lead_profile()` and pass its fields down. `email_example.md` is the one remaining file-based piece: a Markdown style/structure reference the drafting prompt is told to follow (tone, section shape, hard-break formatting), loaded via the cached `get_email_example()` (raises `FileNotFoundError` if missing) -- it stayed file-based rather than moving into `Profile` since it's about *how* things are said, not per-user/business content. A `Profile.signature_block` needs the same two-trailing-space-per-line Markdown hard-break convention `email_example.md` documents, or it collapses into one run-on line when rendered as HTML.

**Gemini is accessed two different ways, deliberately.** Drafting (ranking + subject/body in `draft_email()`) goes through `langchain_openai.ChatOpenAI` pointed at Gemini's OpenAI-compatible endpoint (`GEMINI_BASE_URL` in `lead_gen.py`) — `make_llm()` is the one place this is wired up (model name, base URL, API key from `GOOGLE_API_KEY`, temperature). Website/contact lookup (`find_website()`, `find_contact()`) goes through the native `google-genai` SDK (`make_genai_client()`) instead, because Google Search grounding (the `google_search` tool that lets Gemini actually search the web rather than answer from parametric memory) is not exposed through the OpenAI-compat endpoint — only through the native API. Both hit the same `generativelanguage.googleapis.com` API and the same `GOOGLE_API_KEY`; the split exists purely because grounding requires the native client. This replaced an earlier Tavily-based search implementation (`langchain_tavily.TavilySearch`) — Tavily is no longer used anywhere in this codebase. `make_llm()`, `make_genai_client()`, and `process_unprocessed_leads` are deliberately imported lazily (inside a function, not at module top) by the GUI apps that use them, specifically so opening a Tkinter window never triggers an API-key check or client construction — that only happens once the user actually clicks Process/Verify.

**Single-window app: `main_app.py` embeds, it doesn't open new windows.** Every app class (`LeadRunsApp`, `LeadsApp`, `VerifyEmailApp`, `ProfileApp`) is still fully standalone -- own `if __name__ == "__main__": main()`, own DB session, and its `__init__(self, root, ...)` still works whether `root` is a real `tk.Tk`/`tk.Toplevel` (when run directly, e.g. `python profile_app.py`) or a plain `ttk.Frame` (when embedded). The only thing gated on which: `self.root.title(...)` and each app's own `_center_window(...)` call, both wrapped in `if isinstance(root, (tk.Tk, tk.Toplevel)): ...` in every app's `__init__` -- a bare `ttk.Frame` has neither `.title()` nor `.geometry()`. Everything else (`.after()`, `.update_idletasks()`, `.clipboard_*()`, building child widgets via `ttk.Frame(self.root)`) works identically either way since those are `Misc`-level methods every widget has, not just windows.

`main_app.py`'s `open_app(key)` clears `self.content_frame` (destroying whatever was embedded before -- there is only ever one embedded app at a time, matching "one consolidated window" rather than several simultaneously-open ones) and constructs the new app class into it. The window itself is sized once, in `__init__`, to `MAIN_WINDOW_SIZE` -- the largest (width, height) across `APP_CONTENT_SIZE`'s per-app entries (roughly each app's old standalone-window size) -- and never resized again after that, deliberately: switching apps only swaps what's inside `content_frame`, so the window doesn't visibly jump size each time, and there's always enough room for an app's own internal detail panels (profile_app's edit form, leads_app's edit/send panel) without needing to react to them appearing. A smaller app (e.g. `verify_email`, whose own entry is much smaller) just leaves margin around it rather than shrinking the window to fit. `main_app.py`'s Profile `ttk.Combobox` is populated from `db.Profile` (`refresh_profiles()`, called on startup and whenever `profile_app.py` reports a change via an `on_change` callback main_app wires onto the instance it creates) and tracks `self.active_profile_id`; `PROFILE_AWARE_APPS` (currently `{"lead_runs", "leads"}`) lists which embedded apps get that id passed in at open time (`app_cls(self.content_frame, active_profile_id=...)`) and pushed live updates via a `set_active_profile_id()` method on the instance if the dropdown changes while that app is the one currently embedded. `lead_runs_app` uses it to tag newly-scraped leads; `leads_app` uses it to seed/update its own **Profile** filter dropdown (same pattern as its existing Category filter -- `_load_profile_choices()` builds an email→id map, `load_leads()` filters `Lead.profile_id` by it) so switching the active profile changes which leads are shown, without needing to rebuild the whole embedded app. `verify_email_app` isn't in the set since it has no lead/profile data at all. Note this is separate from *sending*: which address a lead is sent from is still governed by that lead's own linked Profile (`lead.profile.email`), not whichever one is "active" in the dropdown -- the dropdown only affects what's newly tagged and what's currently shown/filtered. Each GUI app that does slow/blocking work (API calls, SMTP) runs it on a background `threading.Thread` and polls a `queue.Queue` via `root.after(100, ...)` — never blocking the Tk mainloop (note: switching away from an app mid-background-task doesn't cancel that thread, a pre-existing gap carried over from the old Toplevel-close behavior, not something this change fixed or worsened). All five GUI scripts repeat the same small Windows-specific shim at the top (pointing `TCL_LIBRARY`/`TK_LIBRARY` at `<base>/tcl/tcl8.6` etc. before `tkinter` is imported) to work around a python.org-installer Tcl/Tk path mismatch — keep it if you touch these files, and add it to any new Tkinter entry point.
